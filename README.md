## Команди:

# Завдання 2 — Масштабування до 3 реплік

## Команди:
docker compose down  
docker compose up -d --scale web=3  

## Результат:
Запущено 3 репліки web. Hostname змінюється при оновленні сторінки, оскільки nginx розподіляє запити між контейнерами (round-robin балансування).

# Завдання 3 — Stateless-пастка

## Результат:
Лічильник поводиться нестабільно: 1 → 3 → 7 → 2 → 5 ...

## Скріншот:
![counter](images/task3.png)

## Пояснення:
Лічильник зберігається в пам’яті процесу (in-memory) кожної репліки окремо. Через балансувальник nginx запити потрапляють у різні контейнери, тому кожен бачить своє значення. Через це виникають “стрибки” та розсинхронізація.

# Завдання 4 — Redis (виправлення стану)

## Команди:
docker compose down  
$env:USE_REDIS="true"  
docker compose up -d --scale web=3  

## Результат:
Лічильник працює правильно і зростає послідовно: 1, 2, 3, 4...  
Додано Redis як спільне сховище стану.

## Скріншоти:
![redis](images/task4-ps.png)  
![counter](images/task4-counter.png)

## Пояснення:
Redis виступає централізованим сховищем стану. Усі репліки використовують одне спільне значення, тому дані синхронізуються між контейнерами.

# Завдання 5 — Відмовостійкість

## Команда:
docker kill <container_id>

## Результат:
Одна репліка зупинена, але система продовжує працювати. Сайт доступний, лічильник працює.

## Скріншоти:
![ps after kill](images/task5-ps.png)  
![site](images/task5-site.png)

## Пояснення:
Користувач не помітив відмови завдяки nginx-балансувальнику, який перенаправляє запити на доступні репліки. Це демонструє redundancy та self-healing у системі.

# Відповіді на питання

## 1. Горизонтальне vs вертикальне масштабування
Горизонтальне масштабування дешевше і гнучкіше, оскільки дозволяє додавати нові сервери. Вертикальне обмежене фізичними ресурсами одного сервера і швидко досягає межі.

## 2. Проблема stateless моноліту
При запуску кількох екземплярів користувач може втратити сесію або бачити різні дані, наприклад, зникнення кошика або повторний логін.

## 3. Аналоги Redis у хмарі
AWS ElastiCache, Azure Cache for Redis, GCP Memorystore.

## 4. SLA і redundancy
SLA системи з кількома незалежними репліками значно вищий, оскільки ймовірність одночасного падіння всіх інстансів низька. Redundancy підвищує надійність і “множить дев’ятки”.

## 5. Що не масштабується горизонтально
Монолітні системи з локальним станом або in-memory сесіями, оскільки вони не мають спільного сховища даних.
