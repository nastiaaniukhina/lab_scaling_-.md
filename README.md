# Завдання 1 — Запуск однієї репліки

## Команди:
docker compose build  
docker compose up -d  

## Результат:
Запущено один контейнер web. Hostname не змінюється при оновленні сторінки, оскільки обробка запитів відбувається одним контейнером.

# Завдання 2 — Масштабування до 3 реплік

## Команди:
docker compose down

## Результат:
Запущено 3 репліки web. Hostname змінюється при оновленні сторінки, оскільки nginx розподіляє запити між контейнерами (round-robin балансування).

## Пояснення:
Лічильник поводиться нестабільно, тому що його значення зберігається в пам’яті процесу (in-memory) кожної репліки окремо. Після запуску кількох контейнерів кожна репліка має власну незалежну копію стану. Балансувальник nginx розподіляє запити між різними інстансами, тому кожне натискання кнопки може оброблятися різними контейнерами. Через це значення лічильника не синхронізується між репліками і виникають «стрибки» або навіть зменшення чисел. Це демонструє проблему відсутності спільного сховища стану в масштабованій системі.

# Завдання 4 — Redis (виправлення стану)

## Команди:
docker compose down  
$env:USE_REDIS="true"  
docker compose up -d --scale web=3  

## Результат:
Лічильник працює правильно і зростає послідовно: 1, 2, 3, 4, 5...  
Додано Redis як спільне сховище стану.

## Пояснення:
Redis виконує роль централізованого зовнішнього сховища стану, де зберігається значення лічильника. Завдяки цьому всі три репліки працюють не з власною пам’яттю, а з одним спільним джерелом даних. Тому незалежно від того, на яку репліку потрапляє запит, усі вони «бачать» і оновлюють одне й те саме значення лічильника.

# Відповіді на питання

## 1. Горизонтальне vs вертикальне масштабування
Горизонтальне масштабування дешевше і гнучкіше, оскільки дозволяє додавати нові сервери. Вертикальне обмежене фізичними ресурсами одного сервера і швидко досягає межі.

## 2. Проблема stateless моноліту
При запуску кількох екземплярів користувач може втратити сесію або бачити різні дані, наприклад, зникнення кошика або повторний логін.

## 3. Аналоги Redis у хмарі
AWS ElastiCache, Azure Cache for Redis, GCP Memorystore.

## 4. SLA і redundancy
SLA системи з кількома незалежними репліками значно вищий, оскільки ймовірність одночасного падіння всіх інстансів низька. Redundancy підвищує надійність і “множить дев’ятки”.

## 5. Що не масштабується горизонтально
Монолітні системи з локальним станом або in-memory сесіями, оскільки вони не мають спільного сховища даних.
